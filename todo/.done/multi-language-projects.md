# Multi-language project support

## Problem

selfdoc's `language` config field is singular — one project, one language. Code extraction directives (`ref`, `table-schema`, `prose-desc`, `code-help`) dispatch to a single extractor. This makes selfdoc unable to fully document multi-language monorepos, which are common (e.g., a project with a Python server, Go router, TypeScript frontend, and Zig runtime).

Today, non-primary-language components must be documented with either static prose (which drifts) or custom directive scripts (workarounds). The architecture table, component descriptions, and API references for non-primary components go stale because there's no extraction mechanism for them.

## Context

Discovered while investigating why a multi-language monorepo's CLAUDE.md (auto-generated by selfdoc) had stale/incomplete descriptions for many of its directories. The template used `"language": "python"` with a single source path, so only Python modules got dynamic extraction. Components in Go, TypeScript, and Zig were described in handwritten static prose that drifted over time.

selfdoc already has extractors for Python, Go, and TypeScript — the machinery exists, it's just not reachable from a single-language config.

## Proposed solutions

### Option A: Per-directive language override

Add an optional `lang` attribute to code extraction directives:

```markdown
:-: ref path="router" lang="go"
:-: ref path="framework/src" lang="typescript"
:-: table-schema path="server/src/myapp/config" lang="python"
```

When `lang` is present, the resolver dispatches to that extractor instead of the global one. When absent, falls back to the global `language` as today.

- Pros: minimal config change, backward compatible, explicit per-directive
- Cons: must specify `lang` on every directive for non-primary components, `source` paths still need to cover those directories

### Option B: Per-source-path language mapping

Change `source` from a list of strings to a list of objects:

```json
{
  "source": [
    {"path": "server/src/", "language": "python"},
    {"path": "router/", "language": "go"},
    {"path": "framework/src/", "language": "typescript"}
  ]
}
```

The resolver infers the language from which source path the target falls under. The top-level `language` becomes optional or a default fallback.

- Pros: configure once, all directives auto-dispatch correctly
- Cons: breaking change to source schema (or needs backward-compat handling for plain strings), more complex resolution logic

### Option C: Both

Per-source-path mapping for the common case, per-directive override for edge cases. Option B as the primary mechanism, Option A as an escape hatch.

## Affected files

- `selfdoc/config.py` — schema for `source` and/or new `lang` attribute validation
- `selfdoc/resolver.py` — dispatch logic to select extractor based on path or directive attr
- `selfdoc/content.py` — pass language context to content directives that delegate to extractors
- `selfdoc/extractors/__init__.py` — lookup by language name (already exists as `EXTRACTORS` dict)

## Effort estimate

Option A alone: small — add `lang` attr parsing in resolver, look up extractor, pass through. Maybe a day.

Option B alone: medium — schema migration for `source`, path-to-language resolution logic, backward compat for plain string lists. A few days.

Both: medium — Option A is trivial once B exists.
