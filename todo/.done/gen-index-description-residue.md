# gen-index description: residue after the partial fix (wrong name for multi-source projects; legacy pages never heal)

## Context

An earlier todo ("gen-index-description-hardcodes-selfdoc", now in `todo/.done/`) reported
that every consumer's generated `docs/gen-index.md` carried a frontmatter description
naming selfdoc itself. The generator side of that was fixed (the "content-aware
description with seeded marker" work, released by v0.29.0): `_generate_index_content`
(`selfdoc/gen.py`, description built around line 383) now composes
"API reference index for {project_name} …" instead of a hardcoded string, and the todo
was moved to `.done` (commit `5427a50`, a pure rename with no code).

Verification against a real consumer shows the fix is **partial**. Two residues remain;
this todo covers them. (Per todo immutability, the `.done` file stays untouched — this is
a new, self-contained item.)

## Residue 1 — `project_name` is derived from the first source path's basename

`_generate` (gen.py, around lines 512-517) computes `project_name` as
`source_entries[0]["path"].strip("/").split("/")[-1]`, falling back to the basename of
the project root only when that strips to empty.

- Single-source projects with `path: "."` get the right name via the fallback.
- **Multi-source projects get the basename of whichever source entry happens to be listed
  first** — e.g. a monorepo listing 26 package `src/` paths gets a description naming one
  internal package (something like "API reference index for vd_core …") rather than the
  project. Wrong metadata, and arbitrary: reordering `source` entries changes the
  project's advertised name.

There is no top-level project-name key in `selfdoc.json` today (checked against the
config schema: version/source/docs/output/base_url/description/branding/… — no `name`).
Candidates for an authoritative name, in order of preference:

1. The manifest name (`.selfdoc/manifest.json` has a `name` field derived at gen time —
   verify how IT is computed; if it shares the same basename derivation, fixing one
   should fix both from a single source of truth).
2. A new optional top-level `name` key in `selfdoc.json` (explicit beats derived; the
   config loader hard-errors on unknown keys, so this is a schema addition).
3. `config["description"]` / `branding.tagline` as descriptive fallbacks, and a generic
   "API reference module index" when nothing is configured — generic beats wrong.

## Residue 2 — legacy pages with the old wrong description never heal

The seeded-marker logic preserves any existing description the generator does not
recognize as its own seed. Pages generated by pre-fix selfdoc carry the OLD hardcoded
phrase ("Auto-generated API reference index for the selfdoc package — browse all public
modules…") **without** the new seeded marker, so the fixed generator treats them as
hand-customized and preserves the lie indefinitely. Empirically confirmed: a consumer
project regenerated docs several times with a post-fix selfdoc (editable HEAD) across
multiple releases and the old description survived every run.

Fix options:

1. **Recognize the legacy seed phrase(s) as machine-seeded** (a small allowlist of the
   old hardcoded description patterns) and reseed them on the next gen. Surgical;
   preserves genuinely hand-customized descriptions.
2. **Always reseed gen-index.md's description** — the page is `generated: true` and its
   description was never meant to be hand-owned; unconditional ownership is defensible
   for this one page (and only this page).
3. Do nothing and document that affected consumers must hand-delete the page once.
   Weakest: silent wrong metadata persists by default.

Option 1 (or 2 scoped strictly to gen-index) is recommended.

## Interaction with the staleness system

The old wrong description on a `generated: true` page is also what fed the
STALE001/DRIFT001 deadlock reported in `todo/skeleton-cli-page-staleness-deadlock.md`
(consumers had to hand-edit `.selfdoc/hashes/hashes.json` during releases). Fixing both
residues removes gen-index from that deadlock class; the skeleton todo still covers the
general case. If both are worked on together, land the reseed BEFORE the skeleton
exemption so the corrected description establishes the new baseline rather than the lie
being exempted into permanence.

## Red-green tests

- Multi-source name: a gen fixture whose `selfdoc.json` lists two+ source entries and an
  authoritative name (per whichever mechanism is chosen) asserts the generated
  description names the PROJECT, not the first source dir's basename. Fails today.
- Legacy reseed: a fixture `docs/gen-index.md` pre-populated with the old hardcoded
  phrase (no seeded marker) asserts one `gen` run replaces the description with the new
  correct one. Fails today.
- Preservation guard: a fixture page whose description is genuinely hand-customized
  (arbitrary text, not matching any seed pattern) asserts gen still preserves it —
  protecting the property the seeded-marker logic exists for.
- Existing anchors: gen tests live in `tests/test_gen.py`; description/staleness
  interplay tests in `tests/test_staleness.py` and `tests/test_check.py`.

## Affected files

- `selfdoc/gen.py` — `_generate_index_content` (description build ~line 383) and
  `_generate` (`project_name` derivation ~lines 512-517).
- `selfdoc_core/config.py` — only if adding the optional top-level `name` key.
- Manifest generation (`selfdoc/manifest.py` or equivalent) — if unifying the name
  source with the manifest's `name`.
- `tests/test_gen.py` (+ staleness tests if the reseed touches hash baselines).

## Effort

Small–medium. Name derivation + reseed allowlist are each an hour-ish with tests; the
config-key route adds schema + docs. The main care point is not breaking the
preservation property for genuinely hand-edited descriptions.
